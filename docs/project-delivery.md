# 让评委看懂，也经得起追问

**先有能演示、能复算的东西，再做PPT。** 这一页适合软件、创新作品和数据项目；具体赛项格式、时长和AI范围优先。[数模论文另看完整教程](math-modeling.md)。

[选赛](competition-playbook.md) · [找数据](data-sources.md) · [可复制工作区](../templates/contest-starter/README.md)

## 1. 每个评分点，都有一件能拿出来的证据

| 评委问什么 | 交什么更直接 | 最容易露馅的地方 |
| --- | --- | --- |
| 你解决谁的问题？ | 真实场景、获准访谈/观察、明确用户动作 | 用AI虚构访谈，需求只有口号 |
| 跟已有方案差在哪？ | 同数据、同机器、同指标的基线与改进 | 挑最好的一次，比较条件不一样 |
| 真能运行吗？ | 同一版本源码、部署步骤、真实演示 | 视频是概念动画；代码跑的是旧版本 |
| 数据可信吗？ | 原表、数据字典、来源台账、清洗记录 | 图表无出处，合成数据写成真实调查 |
| 到底是谁做的？ | 分工、变更、AI使用和人工判断记录 | 把开源底座或导师积累全部写成个人原创 |
| 出问题怎么办？ | 空输入、断网、坏文件、接口失败等测试 | 演示环境一换就报错，没有恢复方案 |

复制 [评分-证据表](../templates/contest-starter/score-evidence.csv)，先填评分原文，再填验收动作；不要倒过来给现有功能硬编评分项。

## 2. 项目书、商业计划书和论文，不用同一个模板硬套

| 材料 | 核心问题 | 你得先有 |
| --- | --- | --- |
| 技术/项目说明 | 做什么、怎么实现、能否重现 | 架构、代码、测试、边界 |
| 商业计划书 | 谁需要、凭什么选你、成本与收入怎样成立 | 真实需求和成本；预测明确标假设，没营收就写没营收 |
| 数据/建模论文 | 问题、假设、方法、结果和结论怎样对应 | 可复跑结果、基线、检验、限制 |

字体统一、图表清楚只是基本要求。真正要核的是：摘要、PPT、论文、视频和代码中的数字、版本、功能是否一致。

## 3. 路演先搭七个问题

按当届时长取舍，不固定要求七页：

1. 谁遇到什么具体问题？
2. 现在怎么办，缺口在哪里？
3. 你的方案实际怎么用？尽快展示真实演示。
4. 用什么证据说明比基线好？
5. 哪些条件下会失败，哪些尚未完成？
6. 团队分别做了什么，哪些资源获准使用？
7. 参赛要展示的最终价值是什么，下一步怎样验证？

预先练短版、完整演示版和故障备用版。现场断网用允许的本地演示或录屏，并明确它是备用录屏，不冒充实时系统。

## 4. 让 Agent 做一次“挑错评委”

~~~text
请读取当前源码、results、docs、PPT文稿和演示脚本，按 inputs/ 的正式评分表验收。
建立 docs/score-evidence.csv：评分原文、验收动作、实际证据文件、版本/运行日期、缺口、负责人。没有实际证据就写缺失。
逐项核对跨文件的数字、图表、功能和版本；从结果文件反查图注和摘要，不手填漂亮数字。
在规则允许范围内补齐部署说明、真实测试、图表和表达，禁止编造访谈、运营、营收、合作、专利或奖项。
再给出12个最可能被追问的问题。每个回答必须指向现有证据；答不出的写待验证与具体补验动作，不编答案。
最后按当届格式整理提交清单，核匿名、页数、视频时长、文件格式、AI披露和作品复用限制；不要自动提交。
~~~

## 5. 比完以后，留下下一次真能用的底座

归档 `源码 + 固定依赖 + 原始数据出处 + 结果 + 演示 + 文书 + 反馈 + 个人贡献`。证书另存，项目失败和未获奖也记录。

简历描述使用真实的“问题 → 你的工作 → 可核验结果”，不要拿模板里的百分比、融资额或奖项套自己。复用去别的比赛前，重新检查资格、主题、已获奖作品限制和新增贡献。
